# 実行計画：ファイルリストのUI整合性と可変幅の復元

## 1. 背景と目的
ファイルリストにおいて、5,000件以上のファイルを高速に扱うための「個別再描画（性能向上）」を導入した際、ヘッダーとデータ行の実装が分離し、列幅の同期が失われた。また、性能確保のために列幅を固定化したことで、以前の「ウィンドウ幅に合わせた可変幅」というUXが損なわれた。本計画では、これらを高次元で両立させる。

## 2. 現在の課題
- **列のズレ**: ヘッダーと `_FileRow` で余白（`SizedBox`）や `flex` の指定が微妙に異なり、右側の列ほどズレが蓄積している。
- **可変幅の喪失**: `LayoutBuilder` の配置ミスにより、ウィンドウを広げても列が広がらない、または計算エラーが発生する。
- **冗長な定義**: 幅の変数が複数の場所に散らばっており、メンテナンス性が低下している。

## 3. 解決策
### 3.1 共通カラム構成 (Column Configuration) の導入
列の定義（最小幅、flex比、ラベル、キーなど）をひとつのリストまたはクラスとして定義する。
- ヘッダー生成時にこのリストをループして `Row` を構築する。
- `_FileRow` 生成時にも同じリストをループして `Row` を構築する。
- これにより、定義を一箇所変えるだけで、ヘッダーと全行が100%同期する。

### 3.2 レイアウト構造の適正化
`LayoutBuilder` を `SingleChildScrollView` の「外側」に配置する。
1. `LayoutBuilder` で現在の利用可能な最大幅を取得。
2. 全列の最小幅の合計を計算。
3. `max(画面幅, 最小幅)` をリスト全体の幅として採用。
4. これにより、広い画面では `Expanded` で広がり、狭い画面では正しく横スクロールする。

### 3.3 手動リサイズ機能の復元
各列の境界にドラッグ可能なハンドルを実装する。
- 幅のデータは `double` 型の絶対値（px）で管理する。
- ドラッグ操作によりリアルタイムに幅を更新し、ヘッダーと全行に反映させる。
- これにより、ユーザーが任意に列幅を調整できる「ファイラーとしての本来の挙動」を取り戻す。

## 4. 実施ステップ
1. [x] **共通定義の作成**: `_FileColumn` クラスの導入。
2. [ ] **幅の状態保持**: 各列の現在の幅を保持する仕組みを導入。
3. [ ] **リサイザーハンドルの実装**: ヘッダー間にドラッグ領域を作成。
4. [ ] **データ行の絶対幅適用**: `Expanded` を廃止し、指定された width を厳密に適用。
5. [ ] **検証**: ズレの解消と手動リサイズの動作確認。

## 5. デグレ防止策
- `ChangeNotifierProvider.value` による個別再描画ロジックは一切変更しない。
- `RenameEngine.buildDiffTextSpan` の呼び出し引数を厳密に維持する。
- `DirectoryProvider` の既存メソッド（リネーム実行等）への影響を与えないよう、UI層のみを修正する。
