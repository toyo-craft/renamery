# 自動アップデート機能の実装戦略調査報告書

## 1. 目的
ReNameryのユーザー体験（UX）向上のため、ユーザーが手動でダウンロードサイトを訪れることなく、アプリを最新の状態に維持できる「自動アップデート」の実現可能性と、OS間の差異、および破壊的変更へのリスク対策を調査する。

## 2. 調査結果サマリー
Flutter公式としての「全OS共通・全自動」更新機能は提供されていないが、以下の3つのアプローチを組み合わせることで、OSの差異を最小限に抑えた実装が可能である。

### 2.1 アプローチの種類
1.  **公式ストアの活用 (Microsoft Store / Google Play)** 【推奨】
    *   OS標準のバックグラウンド更新機能を利用。
    *   実装・メンテナンスコストが最小で、最も安全。
2.  **パッケージによる通知と誘導 (upgrader等)**
    *   起動時に最新バージョンをチェックし、更新ダイアログを表示。
    *   ストアまたはGitHubのダウンロードページへ誘導する。
3.  **コードプッシュ (Shorebird)**
    *   バイナリ全体の更新なしに、Dartコードの修正のみを配信・適用。
    *   現在Android/iOSがメイン。デスクトップは発展途上。

## 3. OSごとの実装の差異と難易度

| OS | 実装難易度 | 実態と制約 |
| :--- | :--- | :--- |
| **Windows** | 低〜中 | MSIX（ストア版）なら全自動。MSI（野良版）はインストーラーのDL・実行が必要。 |
| **Android** | 中 | Google Play版は全自動。APK（野良版）は権限許可と手動上書きが必要。 |
| **Linux** | 高 | `.deb` はパッケージマネージャ（apt等）に委ねるのが一般的。自己更新は非推奨。 |

## 4. 破壊的アップデートへの対策
自動更新によるクラッシュやデータ消失を防ぐための設計指針。

1.  **セマンティックバージョニング (SemVer) の厳守**
    *   メジャーバージョンアップ（X.0.0）時は自動更新を止め、手動確認を促す。
2.  **強制アップデート (Force Update) フラグの導入**
    *   脆弱性修正時などに、特定のバージョン以下での利用を制限する仕組み。
3.  **データマイグレーションロジックの徹底**
    *   設定ファイルやデータベースの構造変更時、古いデータからの変換処理を必ず挟む。

## 5. ReNameryにおける推奨ロードマップ

### 第一段階：新バージョン通知の実装
`upgrader` 等のパッケージを導入し、GitHubタグを監視。最新版がある場合にダイアログを表示してリリースページへ誘導する機能を実装する。

### 第二段階：ストア経由の配布開始
Windows版（MSIX）をMicrosoft Store、Android版をGoogle Playへ公開し、OS標準の自動更新サイクルに乗せる。

### 第三段階：バイナリ自動更新（野良配布版）
ストアを利用しないユーザー向けに、アプリ内でAPK/MSIをダウンロードし、インストーラーを自動起動するロジックを検討する。
